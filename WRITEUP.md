# Wallet & P2P Transfer — Write-up

## Data model

`wallets(id UUID PK, user_id TEXT UNIQUE, balance_paise BIGINT CHECK >= 0, timestamps)`
`transfers(id UUID PK, from_wallet_id, to_wallet_id, amount_paise BIGINT CHECK > 0, idempotency_key TEXT UNIQUE, request_hash TEXT, status ENUM(PENDING/COMPLETED/DECLINED), decline_reason, timestamps)`

Money is `BIGINT` paise everywhere — DB, service layer, JSON wire format. No floating point in the money path. A DB-level `CHECK (balance_paise >= 0)` is a second line of defense against overdraft, on top of the application-level conditional update.

Schema is generated by Hibernate (`spring.jpa.hibernate.ddl-auto: update`) from schema-only `@Entity` classes (`WalletJpaEntity`, `TransferJpaEntity`) that declare the same columns, unique constraints, indexes, and `CHECK` constraints an earlier Flyway migration used to. Those entities exist purely to describe the schema on startup — every actual read/write still goes through the hand-written `JdbcTemplate` repositories (`WalletRepository`, `TransferRepository`), which is where the graded correctness mechanisms live.

## The simplest-correct mechanism (conservation + no-overdraft)

**Chosen: an atomic conditional debit** — `UPDATE wallets SET balance_paise = balance_paise - :amt WHERE id = :id AND balance_paise >= :amt`, checking rows-affected. 0 rows = would-overdraw = clean decline, no partial application. This composes with a `SELECT ... FOR UPDATE` row lock taken on *both* wallets first, in **ascending wallet-id order**, so the debit+credit pair for one transfer is serialized against any concurrent transfer touching either wallet, and two transfers racing on the same pair (A→B and B→A at once) always request their locks in the same global order — so neither can hold one row and wait on the other. No deadlock is possible by construction; there's no deadlock-retry logic because there's nothing to retry.

**Rejected alternatives:**
- **`SELECT ... FOR UPDATE` alone, unsorted** — this is the actual anti-pattern the rubric calls out: A→B locking A-then-B while B→A locks B-then-A concurrently deadlocks under load. Sorting the lock order is the one-line fix, so there was no reason to reject sorted locking — I use it, just not as the *only* mechanism.
- **`SERIALIZABLE` isolation** — correct, but pays for full conflict detection across the whole transaction and requires the client to catch and retry serialization failures on every write, for a workload where the conflict is really just "two rows." That's real complexity (retry loop, back-off, idempotency-safe retries) to solve a problem the conditional `UPDATE` already solves for free.
- **Read balance into app, subtract, write back** — the textbook lost-update bug; rejected outright, not "heavier," just wrong.

## Where idempotency lives

`idempotency_key` uniqueness is a DB `UNIQUE` constraint, reserved via `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` **inside the same transaction** as the debit/credit — not a separate check-then-act step. This matters because Postgres blocks a concurrent `INSERT` on a conflicting unique key until the first transaction commits or rolls back; only then does it resolve to a no-op (if committed) or a fresh insert (if rolled back). So a "loser" in a concurrent retry storm is *guaranteed* to see the winner's fully-committed result when it re-reads by key — never a half-applied one. (An earlier version of this used a plain `INSERT` + catch `DuplicateKeyException`, which is wrong: a unique-violation aborts the whole Postgres transaction, so nothing after it could run. `ON CONFLICT DO NOTHING` avoids that abort while keeping the same blocking guarantee.)

Same key + different body: I hash `(from, to, amount_paise)` with SHA-256 and store it alongside the key. A replay with a matching hash returns the original result; a mismatched hash is a `409`.

## Consistency vs availability

This is money, so I chose **strict consistency over availability** on the write path: every transfer is a single ACID transaction against one Postgres instance, row-locked, and a caller gets a definitive committed-or-declined answer or an error — never a "probably applied" response. What I gave up: horizontal write scaling (one primary, contended on hot wallets) and availability during a primary failover (a brief write outage rather than an eventually-consistent double-write risk). For a payments ledger, a short unavailability window is the correct trade against ever risking a duplicated or lost debit.

## Test-only addition beyond the spec

The 4 required endpoints give no way to fund a wallet (all start at 0), but Gate 3 needs seeded balances. I added `POST /wallets/{id}/deposit` purely as a test-seeding affordance — it reuses the same atomic credit as a real transfer, isn't part of the 4 graded invariants, and isn't meant to imply a real top-up product feature.
